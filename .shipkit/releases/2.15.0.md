# 2.15.0: Audio and video in, video out
2026-09-28

## Vars

### Audio and video inputs
<!-- weight: major -->
`v.audio(path)` and `v.video(path)` join `v.image(path)`: the same plain path value, the same TUI picker (filtered to that medium), the same serve file gate. `await someVar.loadInWorkflow(wf)` uploads the file and returns its loader node: `LoadImage`, `LoadAudio` or `LoadVideo`. The file is named by its hash, so a rerun does not upload it again. An empty var throws `MediaVarEmptyError` (`ImageVarEmptyError` is the same class).

## Runs

### Video outputs come back to your code
<!-- weight: feature -->
`execution.videos` lists every video an output node wrote (`SaveVideo`, `SaveWEBM`, VideoHelperSuite's `VHS_VideoCombine`), with the same shape as `execution.audios`. An animated webp or gif stays an image. Before, a saved mp4 landed in `execution.images`.

## Web panel

### Drop media on a var
<!-- weight: feature -->
An image, audio or video var takes a file dropped from the desktop, or a result dragged from the gallery. Every result also carries one `→ <var>` button per var of its medium in the open workflow. An unsaved result is uploaded first, so the var always holds a local path. A drop of the wrong medium is refused with the reason on the row.

### The web panel plays video results
<!-- weight: feature -->
In a player, blurred like images when blur is on. The run reply carries `videos: [{ filename, mime, url, absPath }]`, and with saving off `GET /video/<promptId>/<ix>` serves the file from memory.

### `POST /upload` takes files up to about 200 MB
<!-- weight: improvement -->
So a video fits. The other routes keep their 10 MB cap.
