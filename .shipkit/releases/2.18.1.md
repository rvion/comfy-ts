# 2.18.1: Installs that say when they cannot tell
2026-11-17

## Manager

### An install can say that its outcome is unknown
<!-- weight: feature -->
`manager.installModelOutcome(model)` and `manager.installPluginOutcome(pack)` return `'installed' | 'failed' | 'unknown'`. `unknown` means the client lost sight of the task while the Manager may still be installing: refetch the list and read the status before you install again. `installModel` and `installPlugin` still return `true` only for a verified install.

### A failed status request no longer ends an install
<!-- weight: improvement -->
The wait goes on until the host has not answered for `timing.pollGraceMs` (default 2 minutes). Before, one failed request made the install resolve `false` while the Manager was still downloading.

### An install removed from the queue fails at once
<!-- weight: improvement -->
On the Manager 4.x default UI, a queue reset from the Manager UI or another client used to leave the install waiting for the whole `installTimeoutMs`, 1 hour by default.

### A pack install is checked against what is installed
<!-- weight: improvement -->
On the Manager 4.x default UI the Manager installs by repo name, and a few repo names belong to another pack. An install the Manager calls successful now fails when the pack does not show up as installed.

### A requirement the host cannot decide is no longer treated as missing
<!-- weight: improvement -->
`host.matchRequirements` returns `false` only for a requirement known to be missing, and warns with the name of each one it cannot decide. `host.checkRequirements(reqs)` returns `{ missing, undecided }`: queue installs for `missing` only. `isModelInstalled` and `isPluginInstalled` are `true` only for a known install, so read `getModelStatus` and `getPluginStatus` to tell "not installed" from "cannot decide".

## Workflows

### A workflow whose subgraphs contain themselves fails at once
<!-- weight: improvement -->
It fails with a `subgraph-cycle` error that names them. Before, the import never returned. Nested subgraphs that would expand to more than 100,000 nodes fail with a `subgraph-too-large` error.

### A long chain of nodes with a missing required input no longer overflows the stack
<!-- weight: improvement -->
It gives the `missing-required-input` error. Importing a large workflow is also faster.
